# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A [Herdr](https://github.com/ogulcancelik/herdr-plugin-examples) plugin (`com.codreamer.herdr.oncall`) that pings Telegram or Feishu when an agent pane goes `blocked` or `done`, and delivers replies back into that pane. On macOS a floating desktop panel (`src/desktop/panel.swift`) comes first and the phone channel is the fallback. Plain ESM Node.js (`.mjs`), Node 18+ (22+ for Feishu replies, which need the global `WebSocket`), **no package.json and no npm dependencies** — only `node:` builtins and global `fetch`. The plugin manifest is `herdr-plugin.toml`; bump `version` there for releases.

## Commands

```sh
# run all tests (node's built-in runner; `node --test test/` with a bare dir path does NOT work)
node --test 'test/*.test.mjs'

# one file / one test by name
node --test test/pair.test.mjs
node --test --test-name-pattern="pairDeepLink" test/pair.test.mjs
```

There is no lint or build step for the JS. The macOS panel is compiled by `bin/install-deps.sh` (Herdr's `[[build]]` step) with `swiftc` into `bin/oncall-panel` (git-ignored); to rebuild after editing `panel.swift`, run `bash bin/install-deps.sh` (about a minute). It lives in the plugin root rather than the state dir because Herdr sets `HERDR_PLUGIN_STATE_DIR` for events and actions but **not** for build commands, so anything the build writes to "the state dir" lands somewhere the hooks never look. Live testing goes through the Herdr CLI (see README): `herdr plugin action invoke <setup|poll|pair|pair-feishu|test|toggle|enable|disable> --plugin com.codreamer.herdr.oncall`, then `herdr plugin log list --plugin com.codreamer.herdr.oncall --limit 5` for real output (`action invoke` only returns JSON immediately). `bash install.sh` links the checkout into Herdr for local development.

To exercise the notify hook by hand without pinging Telegram, run it with an empty token and a short delay against a real pane:

```sh
TELEGRAM_BOT_TOKEN= BLOCKED_DELAY_SEC=5 \
HERDR_PLUGIN_EVENT_JSON='{"data":{"pane_id":"wJ:p1","agent_status":"blocked","display_agent":"codex"}}' \
bash bin/run-node.sh src/hooks/notify.mjs
```

## Architecture

### Process model

Every entry point in `herdr-plugin.toml` runs through `bin/run-node.sh`, because Herdr's server does not have a login-shell PATH. The script hunts for `node` (nvm/fnm/mise/volta/homebrew…), caches the path in `<state>/node-path`, and `exec`s it. If something "can't find node", look there first.

Three kinds of process share `src/lib`:

1. **Event hook** — `src/hooks/notify.mjs`. One-shot, spawned by Herdr on `pane.agent_status_changed`. Reads `HERDR_PLUGIN_EVENT_JSON` / `HERDR_PLUGIN_CONTEXT_JSON` from env. Outbound path only.
2. **Poller** — `src/hooks/poll.mjs`. Long-running, detached child (`src/inbound/poller.mjs` spawns it via `spawnDetached` → `run-node.sh`, pid in `<state>/poller.pid`). Runs two loops side by side: the Telegram `getUpdates` long-poll (pairing + replies), and the Feishu long connection (`connectFeishu`, replies + card taps), each idle with a one-line reason while its channel is unpaired. Deliveries from both go through one `serial()` queue, so two replies never type into panes at once. It is started by `seed.mjs` at build/startup, and `notify.mjs` calls `ensurePoller()` on every event as a self-heal. Any action that touches config calls `restartPoller()`. Its stdout and stderr go to `<state>/poller.log`, timestamped by `withTimestamps()` and rotated once at 256 KB — nothing else captures them, since Herdr's plugin log only sees the action that spawned it and that action exits immediately.
   It rereads `.env` on every pass, so a token filled in after install reaches it without a restart. That rests on two things: `loadDotEnv` never overrides a value the process was *started* with, but a value it read from a file itself follows that file (`setDotEnvValue` marks pairing's write-back the same way); and `startPoller` spawns with `startupEnv()`, the environment minus what the spawner loaded. Handed the hook's loaded values, the poller took them for its own environment, and a fresh install's empty `TELEGRAM_BOT_TOKEN=` stayed pinned until someone ran the `poll` action.
3. **Actions** — `src/actions/*.mjs`. One-shot CLI scripts (setup/install, poll, pair, pair-feishu, test, toggle, seed). `pair-feishu.mjs` is also the one background worker besides the poller: run as `pair-feishu.mjs wait <device code>` (spawned detached, logging to `poller.log`) it holds the QR panel and waits for the scan, so the action itself returns as soon as the code is printed.

### Two on-disk directories (never confuse them)

- **Config dir** — where `.env` lives. Resolved by `configDirPath()` in `src/lib/paths.mjs`: `HERDR_PLUGIN_CONFIG_DIR` → `herdr plugin config-dir <id>` → XDG fallback. `seedConfigEnv()` copies `.env.example` there and non-destructively upgrades missing keys (`NOTIFY_ON`, `BLOCKED_DELAY_SEC`). `.env` survives reinstalls.
- **State dir** — `stateDir()` in `src/lib/paths.mjs`: `HERDR_PLUGIN_STATE_DIR` → Herdr's own `<state home>/herdr/plugins/<id>` when that directory exists (`herdr-dev` for a debug build) → `<state home>/herdr-oncall` for a machine where Herdr has never linked the plugin. Holds runtime files: `enabled` (toggle), `last-notify.json` (debounce), `blocked-delay.json` (delayed-ping ownership), `outbound.json` (Telegram message_id → pane map, 24h TTL), `telegram-offset`, `poller.pid`, `poller.log` (+ `poller.log.1`), `pair.json`, `feishu-pair.json` (the Feishu scan in progress: device code, page, expiry), `panels.json` (pane → open panel pid), `last-skipped-screen.txt` (the screen behind the most recent `skipped` line, to turn into a fixture), `node-path`.

  Herdr sets `HERDR_PLUGIN_STATE_DIR` for events and actions, but **not** for build commands and not for anything you run from a shell — `install.sh` included. Computing Herdr's own path for those cases is not cosmetic: while the fallback was a second directory, a shell-run process and a Herdr-run hook kept separate `poller.pid` files, so `ensurePoller()` could not see the other side's poller. Five of them ended up long-polling one bot token (Telegram allows one, the rest get 409 Conflict), and a stray one that won an update had no `outbound.json` to resolve the pane with, so the reply answered "Reply to a ping so I know which pane." `bin/run-node.sh` is bash and still caches `node-path` under the old path; that one is only a cache, so it re-derives instead of splitting anything.

Tests isolate themselves by pointing these two env vars at `mkdtempSync` dirs; follow that pattern for any new test that touches disk.

### Outbound flow (notify.mjs)

`resolveStatus` → `resolveWorktree` (fills `context.worktree` from `herdr workspace get` and the branch from `herdr worktree list --workspace` when the event did not carry them) → then:

- **done with a menu on screen**: Herdr misses some questions. Claude Code's multi-question form has been reported `done`, and then `idle`, with the form still waiting, and all that opened was a done panel showing the form as text with nothing to press. So a `done` event reads the visible screen first, and when `screenHasOpenMenu` finds an open menu the event is promoted to `blocked` (logged `menu on screen · <where> · herdr said done`) and everything below runs as it would for a real block. The check comes *before* the `NOTIFY_ON` filter, so a setup that only asks for `blocked` still gets these. This is also why `nextDialog` lets only `working` end its wait early: `done` and `idle` are exactly what Herdr keeps saying the whole time such a form is up.
- **blocked, first gate**: read the pane through `readScreenSettled` (up to 6 tries, 500 ms apart, first non-blank read wins) and require `screenHasLiveDialog`. Herdr's `blocked` is not trustworthy on its own — its detector matches dialog wording anywhere in the recent buffer, so an agent that merely *printed* a permission prompt pins its own pane at blocked (this repo did exactly that to itself while building the parser), and `herdr pane get` can also hand back a stale value from the previous detection pass. No live dialog on screen → log `skipped · … · blocked but no dialog on screen · tail: …` (the last 8 non-blank lines) and write the whole screen to `<state>/last-skipped-screen.txt`, so an unrecognised shape becomes a fixture instead of a silent drop. A screen that is still blank after those retries is never evidence of anything: `decideBlockedReal({ screenReadable: false })` is `false` whatever `herdr pane get` says, and the skip reads `blocked but pane screen empty`. Codex clears and redraws the pane the instant a dialog is answered, and trusting the status through that gap is what opened an empty panel with no body and no buttons.
  The exception is an agent whose lifecycle an integration owns (Herdr 0.9.0: Pi, OMP, Kimi Code, OpenCode, Kilo, MastraCode). `agentDetectionSkipped(paneId)` reads `screen_detection_skipped`; when it is true and `stillBlocked()` agrees, `decideBlockedReal` (pure, in `src/lib/herdr.mjs`) calls the block real even with no menu drawn — logged as `hook-authoritative · <where>`. That ping carries no inline keyboard and no fingerprint — and neither does the desktop panel, since both take their buttons from `dialogChoices(screen, { hookAuthoritative })`, the one gate that keeps the `(y/n)` fallback off an agent with no menu drawn — and `paneMovedOn` watches the status instead of the screen. The `agent get` call is made once per hook process, not on every panel poll.

- **blocked, panel available, `BLOCKED_DELAY_SEC` > 0**: `showPanel` replaces the wait. A button or typed text goes straight into the pane via `deliverReply`, and then the hook looks for the question that *replaces* the one it just answered: a multi-question form advances tab by tab in place, so Herdr fires no second event and a hook that exited after one answer took the panel with it and left the rest of the form to the terminal. `nextDialog` (`src/lib/format.mjs`) polls until a live dialog with a different `dialogFingerprint` appears, the pane goes back to `working`, or it runs out of tries; `MAX_FORM_ANSWERS` caps the chain. Timeout or Esc falls through to the checks below and then Telegram. While the panel is up, `until` is polled every 2s: the dialog leaving the screen (answered in Herdr) closes it and the hook exits; the user arriving at the pane (`userAtPane`: Herdr focused pane + terminal app frontmost via `lsappinfo`) closes it and the remaining delay runs silently before Telegram. `userAtPane` falls back to the focus flag alone when it cannot identify the frontmost app, and that fallback has one exception it cannot do without: the panel is a bare binary with no `CFBundleIdentifier`, so once it started activating itself for the input method it *became* the unidentifiable app in front, every poll read "the user has arrived", and the panel closed itself two seconds after opening — while the user was still reaching for it. `frontmostApp` returns the display name too, and the panel's own name is never the user at the pane. "The dialog is gone" needs two consecutive polls (`consecutiveGate` in `src/lib/desktop.mjs`) and a blank read counts as neither — one tick can land mid-redraw. The panel is not opened at all when the user is already at the pane. A newer blocked event for the same pane kills the older panel (`panels.json`) and the older hook exits as `superseded` — but only a *question* may evict a question: `panelOutranks` keeps a `done` panel from taking a blocked panel's place, which used to make the question disappear without even reaching Telegram, since Claude Code emits both for one pane inside a second.
- **blocked, after the wait**: re-read the pane with `readScreenSettled` and require a live dialog again (not `herdr pane get`), plus `blockedDelayStillMine`.
- Chat ping (`pingRemote`, once per event, to every channel in `remoteChannels()` — the paired ones `CHANNEL` selects — each in its own try so one being down does not cost the other its ping): `shouldDebounce` → `readPaneScreen` (`herdr pane read`; `recent-unwrapped` source for done, `visible` for blocked) → `blockedSnippet`/`doneSnippet` + `parseBlockedOptions` (`src/lib/format.mjs`) → `sendRemote` (Telegram: inline keyboard for blocked options, else force-reply; Feishu: a schema 2.0 card with one button per option, else a text message) → `rememberOutbound(messageId → pane)`, which also stores the dialog's `fingerprint`, parsed `options`, the `channel`, and for a Feishu card its `text`, so the card can be rebuilt after a tap.
- **Blocked body from the session** (`blockedBody` in `notify.mjs`, `sessionDialogBody` in `src/lib/transcript.mjs`): a permission dialog is about a tool call the agent already made, and the session records that call the moment the model emits it — its result only once the user answers (a real Claude Bash approval: called 03:11:41, answered 03:13:00). So the open call is the dialog's subject, whole, where the screen cut the command at the pane width. **Claude Code**: `claudePendingCalls` takes the current turn's `tool_use` blocks with no `tool_result` (none once `end_turn` is last; a user prompt is where the turn began). **Codex**: `codexPendingCalls` takes the calls since the last `task_started` with no `*_output` for their `call_id` (none after a `task_complete`); Codex writes no approval events, only the calls. `describeCall` renders each per tool — Bash command and description, Edit/Write path and lines, WebFetch URL, AskUserQuestion / Codex `request_user_input_async` one candidate per question with every option's description — and names a `witness`, the piece of it the screen must show. `pendingDialog` uses the first candidate whose witness (whitespace and Markdown marks removed, first 40 chars, at least 4) is on screen: a turn can have several calls open (Claude runs tools in parallel) and the dialog asks about one, and a dialog that is not about a call at all (Claude's "Teach auto mode…", a folder-trust prompt) matches nothing. No match, no session, or Codex's code-mode `exec` (its input is JS that calls `tools.exec_command`, so the approved command is buried in code) → `blockedSnippet` as before. The screen's question line (`dialogQuestion`) goes under it, except for a form, whose candidate is the question. **The choices, the keys, liveness and the fingerprint never come from the session** — they are what a reply presses, and the screen is what it presses on. The poller's `followForm` builds a form's next question the same way. The plugin log says `blocked · <where> · body from session|screen`, once per distinct screen.
- **done**: the chat channel is pinged first, then the panel opens with the last answer and a text field; typed text becomes a new prompt. **The answer comes from the agent's own session record, not the screen** (`sessionAnswer`, `src/lib/transcript.mjs`). Reading it off the screen meant guessing which lines were the answer and which were whatever the agent draws around it, and every new footer an agent grew went out as the ping — Codex's `› Ask Codex to do anything` prompt box reads exactly like a sent turn, and the model line and shortcut hints under it made a ping that was nothing but footer. Getting from a pane to its session (`paneSession`) asks nothing of the user. First, the session Herdr's integration reported on `SessionStart` via `pane.report_agent_session`, which `agent get` returns as `agent_session: { agent, kind: "id"|"path", value }`. Failing that, for **Claude Code**, its own per-process record: `herdr pane process-info --pane <id>` names the pane's process group leader and foreground pids, and `~/.claude/sessions/<pid>.json` (`CLAUDE_CONFIG_DIR`) holds that process's current `sessionId` (it follows `/clear` and resume; a `kind` other than `interactive` is a one-shot `claude -p` and is skipped). That is exact and covers sessions started before Oncall was installed; a session with no message yet has a record but no transcript file, and needs none. **Codex** keeps no per-process record — its terminal hands the session to a background server, which holds every thread's writer lock — so a Codex pane is tied to its session only by Herdr's Codex integration, and `ensureIntegrations` installs it (`herdr integration install codex`) from `seed.mjs` on every build and Herdr start, from `install.mjs`, and from the done hook when a Codex pane has no session to find — Codex installed after Oncall would otherwise wait for the next Herdr start, and Herdr's server can run for days — whenever `~/.codex` exists and `herdr integration status` does not say `current`/`installed`. `INSTALL_AGENT_INTEGRATION=0` turns that off. The integration writes a hook into Codex's config; Codex asks once to trust it, and only sessions started afterwards report. Claude Code's integration is never installed by Oncall: it is not needed. Claude Code reports the id and its transcript path; Codex only the id, found as `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl` (a fork is `…-<parent>_<id>.jsonl`, so the match is on the ending). From the file's tail: **Codex**'s answer is the last `event_msg` `task_complete`'s `last_agent_message`, and a `task_started` after it means the turn is not written yet; **Claude Code** writes each content block as its own record, every block of the turn-ending message carries `stop_reason: "end_turn"`, so the answer is the text in that trailing run (narration before a tool call ends in `tool_use` and stays out; `isSidechain` subagent records are skipped). A done event can land a moment before the file has the turn, so an unfinished file is re-read (6 tries, 500 ms apart) — and never answered with the previous turn's message. A long answer keeps its beginning (`capAnswer`). The plugin log says `done · <where> · answer from session|screen`. The screen is used for a pane whose session cannot be found — any agent other than Claude Code and Codex, or a Codex session started before the integration was installed.

  The screen is the fallback, for any pane whose session cannot be found. That read is settled too, but on a different condition: a done event lands the instant the turn ends, which is also when the agent repaints, and it repaints from the bottom — the prompt box, the rules and the mode footer are on screen before the turn above them. That read is not blank, so the gate `blocked` uses would hand it straight back and the ping would carry nothing. `readScreenSettled`'s `ready` predicate takes `doneSnippet(text)` being non-empty instead, so it waits for a read with a turn in it. `doneSnippet` tells the prompt box from a sent turn structurally where it can: when the agent's turns are on screen (`isTurnStart`: `⏺`/`●`, or Codex's `•` at the left edge), a user line with no turn after it is the box, so the answer runs from the user line before it up to the box.

The panel binary speaks a one-line stdout protocol (`button:<i>` / `text:<t>` / `timeout` / `dismiss`), parsed by `parsePanelResult` in `src/lib/desktop.mjs`. Panel debounce uses the keys `panel:blocked` / `panel:done` so it does not interfere with the Telegram debounce. Opening it calls `NSApp.activate`: an input method attaches to the *active application*, not to whichever window holds the caret, so as a `.nonactivatingPanel` the field took raw keystrokes (fine for `y` or `1`) while the IME stayed with the terminal and Chinese could not be typed at all. Activating makes macOS write input-method chatter to stderr on every open, which `panelStderr` drops so a working panel does not log two errors per notification.

### Reading a permission dialog off the screen (`src/lib/format.mjs`)

`screenLines` keeps blank lines and drawn rules — they are the block boundaries, and the old version that filtered them out is what forced guesswork like "take the last N lines". `dialogRegion` then locates the dialog structurally, and both `blockedSnippet` and `parseBlockedOptions` work from that one region:

- **options**: the run of numbered lines at the *bottom* of the screen, found by skipping the trailing key hints and walking up. Taking the first numbered run below the question instead is what once put a workflow's phase list (`1. Review — three lenses…`) on the buttons and dropped the real `1. Yes, run it` as a duplicate index. A more indented non-numbered line inside the run is a wrapped option, and `joinWrappedOptions` puts it back on the label before parsing, so a choice the terminal broke in two is weighed exactly like the same choice on one line — `(esc)` becomes the send key either way, `(shift+tab)` stays prose either way, and the label stops moving when the pane is resized. A tail hanging off the *last* option is the first thing the scan up from the bottom meets, so it is stepped over rather than read as the end of the dialog — but only one that hangs deeper than its option: at or left of the option column, a line ending in `(y)` is content under the list, not part of it. A form's choices put a description on the lines under them, at the very same hanging indent, and joining those on is what put `1. Drop it (Recommended) A failed send gets Home's per-message r` on a Telegram button. Indentation cannot tell the two apart, but width can: a word moves down only when it does not fit, so after a real wrap the line above, a space and the carried word together overrun the pane (`wrappedOnto`, with the pane width taken from the widest line on screen — the rules run the full width — and CJK counted as two columns). The label is the numbered line plus what wrapped off it; from the first line that did not wrap, the rest is description, which stays in the snippet body but never on a button. Labels are cut at 96, the width of the panel button (`panelLabels`); Telegram caps its own at 64. A drawn rule inside the run is crossed only when the line above it continues the numbering downward — Claude Code's tabbed multi-question form puts `4. Chat about this` in its own section under a divider, and stopping at that rule left exactly one useless button.
- **question**: the nearest line above the run that ends in `?` or the fullwidth `？`, stopping at the same structural boundaries as the body walk. Only when there is no numbered run at all (a bare y/n prompt) does it fall back to matching wording (`would you like` / `do you want` / `allow` / `permission`), which is still English-only.
- **start**: if non-blank content sits between the question and the first option, the command is *below* the question (one Codex shape) and the question is the start. Otherwise the content is *above* (Claude Code, Codex "requires approval") and the walk goes up to the first structural boundary: a turn marker (`⏺`/`●`, included — it names the tool), a Codex tool header line, the previous user turn, a drawn rule, or two consecutive blanks. There is deliberately **no line cap**: the input is a single viewport, so the walk is already bounded, and a cap only truncates long commands.
- **render**: `renderBlock` drops rules, trims the edges, and collapses blank runs.
- **shortcuts**: a trailing parenthetical becomes the key to send only when it names one — a single letter or digit, or `esc`/`escape`/`enter`/`return`/`tab`/`space`. Anything else (`(default)`, `(shift+tab)`) stays in the label and the option index is sent instead; the old "alphanumeric and ≤ 8 chars" rule made `1. Yes (default)` type the word `default` into the pane.
- **fingerprint**: `dialogFingerprint` hashes the question, every `key|<option's whole text>`, and the rendered body *above* the first option into 16 hex chars — the body is in there because two Bash approvals in a row ask the identical question with the identical choices and only the command differs, and the option lines are left out of it because they are already hashed per option, so moving the terminal's `❯` marker between choices (or re-wrapping them) must not invalidate a ping. Each option is hashed as its whole text, description included, rather than its button label: where the label ends is judged against a width read off the screen, and a hash must not move with that reading. A choice with no description has the same text either way, so those fingerprints are what they always were. It is what the inbound path compares against the live screen before pressing a key, and hashing only the region is what keeps it stable while a spinner or footer changes underneath.
- **liveness**: `screenHasLiveDialog` says a dialog is *waiting* rather than merely *quoted* — only blanks, drawn rules and chrome may follow it. Getting `isRuleLine` and `isChromeLine` right matters here: the labelled separators the agents draw (`──── ultracode ↯ ─`), the status footers (`➜ repo git:(main) ctx:33% Opus 5`, `» Ask Codex…`) and Claude Code's task list (`4 tasks (3 done, 1 in progress, 0 open)` and its `✔`/`◼`/`◻` rows) all sit under a real dialog, and treating them as content swallows genuine notifications. The task list cost every pane with a todo the panel *and* its buttons, silently, until the skip trace caught it: both liveness and `trailingOptionRun` find the dialog by walking up from the bottom past the chrome, so one unrecognised footer breaks both.

  The error runs the other way too, and is worse: chrome rules that are too *loose* eat real content. `tokens?` matched any short line mentioning the word, so an option whose description read `任何人可从 ai-assistant 取到 ASR token` ended the walk and the ping went out with the first two choices missing. A footer's token count is what makes it a footer, so the rule requires the number. `shift+tab` was the same trap one level down: a long option (`2. Yes, and always allow access to /Users/… for this session (shift+tab)`) wraps past the pane width and leaves its parenthetical on the next line, where the key-hint rule claimed it — the walk stopped there, the panel opened with one button (`3. No`), and the other two choices were stranded in a body that began at the question instead of the turn marker. It happened twice, because the first fix spared only a line that was *nothing but* `(shift+tab)`; with a longer path the wrap carries the word before it too, and `session (shift+tab)` was a footer again. A real key hint says what the key *does* (`shift+tab to cycle`), so its parentheses never hold a bare key, and a line that *ends* in a bare key name in parentheses is never chrome (`endsInKeyParenthetical`).
- **open menu**: `screenHasOpenMenu` is stricter than liveness, and it is the only screen check allowed to overrule Herdr's status (promoting a `done`, or retyping a reply). Liveness alone cannot make that call: when a turn ends on a numbered list, only the empty prompt box and its footer sit below it, which is exactly what sits under a real dialog. A list in prose never has the selection cursor, though, so an open menu also needs `❯`/`›`/`▸` on one of its choices, plus at least two choices so that a numbered draft typed into the prompt box (`❯ 1. now bump…`) does not qualify.

Reading the pane goes through Herdr's socket to the server that owns the PTY, so it works regardless of what is on the physical display — the terminal can be minimised, on another Space, or in an unfocused workspace. Only `userAtPane` (which suppresses the panel) depends on the desktop.

When a dialog shape does not extract cleanly, capture the real screen (`herdr pane read <pane> --source visible --format text`) and add it as a test case rather than tuning a threshold.

### Inbound flow (reply.mjs)

`handleTelegramUpdate` → pairing check (`/start CODE` or bare code while `pair.json` is pending; writes `TELEGRAM_CHAT_ID` via `upsertEnvValue`) → reject any chat other than `TELEGRAM_CHAT_ID` → `resolveReplyTarget` (the `reply_to_message` id looked up in `outbound.json`, else the most recent outbound, and the record is tagged `explicit` when the reply named it) → `deliverReply`, which re-reads the **live** pane status and classifies:

| live status | reply text | herdr command |
|---|---|---|
| blocked | single key / named key (`y`, `esc`, `enter`…) | `pane send-keys` |
| blocked | anything else | `pane send-text` + `send-keys enter` |
| other | anything | `agent prompt` (falls back to send-text on `agent_blocked`) |

The live status is `pane get`'s, with one override: when Herdr says anything but `blocked` while an open menu is on screen (`screenHasOpenMenu`), `deliveryStatus` treats the pane as blocked. `agent prompt` *submits* — it types the text and presses Enter — so on a form Herdr calls `idle`, a `1` picks the first choice, the form moves on to its next tab, and the Enter answers that tab too.

Before any of that, a reply that carries a `fingerprint` is re-verified: `deliverReply` reads the screen again — **whatever `pane get` says**, because Herdr's status lags and a pane it still calls `working` can already have the next dialog drawn on it — and requires a live dialog whose `dialogFingerprint` still matches. A Telegram button lives forever, the dialog it belonged to does not, and a `1` meant for one prompt must not land on the next one. No live dialog on screen is stale too: the dialog this reply was about is gone. A mismatch returns `{ status: 1, stale: true, … }`, nothing reaches the pane, and the ack is `stale · <where> · dialog changed, not sent`. A pane that cannot be read at all logs `fingerprint unverified · <paneId>` and sends anyway. Which replies carry the fingerprint is `replyFingerprint(target)`: only ones that named their ping — an explicit `reply_to_message` or a button tap — since a **bare** message that merely resolves to the most recent outbound is about the *pane*, not about that dialog, and must still deliver as a prompt. The ping's own status gates it too, so a done record is never fingerprint-checked, and records written before fingerprints existed behave exactly as before. The `agent prompt` → `agent_blocked` fallback runs the same check a second time: Herdr answering `agent_blocked` means `pane get` was stale and a dialog *is* up, so the text must not be typed into it unsighted.

Inline-keyboard taps arrive as `callback_query` and take the same `finishDelivery` path; a tap always names its own message, so an id missing from `outbound.json` is acked with `no pane mapped for that button` rather than falling back to the most recent ping. `handleTelegramUpdate` takes its Telegram and Herdr edges (`send`, `answer`, `run`, and `wait` for `nextDialog`) from its `deps` argument, defaulting to the real ones, so the whole inbound path is testable without a network or a live pane.

A reply to a blocked ping that lands in a live dialog is followed, the same way the panel follows a form (`followForm`): the Telegram ping goes out just as its hook exits, so nothing else is left to notice that the form moved to its next tab, and answering the first question from Telegram used to leave the rest of the form sitting in the terminal. `finishDelivery` reads the dialog's fingerprint *before* delivering the reply, and afterwards runs `nextDialog` against it. When a different question appears, it is pinged like any other — its own buttons and fingerprint, stored in `outbound.json` under the first ping's `title` (which `rememberOutbound` keeps for this reason) and `where` — so it can be answered and followed in turn. This blocks the update loop for as long as `nextDialog` waits (up to 8 s; a one-off dialog ends at the first read where the agent is `working`). A follow-on ping that fails to send is logged as `follow-on ping failed · <where>: …`, and the answer that already went through still counts as delivered.

`finishDelivery` and `followForm` do not know which chat they are in: they talk to a channel object (`{ name, reply(text), ping(text, { options }) }`), `telegramChannel(deps)` in `reply.mjs` or `feishuChannel` in `inbound/feishu.mjs`, and a follow-on question goes out on the channel the answer came from. `deps.ack` overrides only the ack, which is how a Feishu card reports on itself.

### Feishu (`src/lib/feishu.mjs`, `src/lib/feishu-ws.mjs`, `src/inbound/feishu.mjs`)

- **Pairing is app registration.** `pair-feishu` calls Feishu's device-flow registration (`accounts.feishu.cn/oauth/v1/app/registration`, `action=begin`, `archetype=PersonalAgent`, the same protocol `lark-cli config init --new` and the official OpenClaw installer use): it returns a device code and a page to scan. Polling that code (`feishuRegistrationWait`) ends with a newly created bot app's `client_id`/`client_secret` and the scanner's `open_id`, so one scan is both the bot setup and the pairing — there is no token to paste. A Lark tenant reports `user_info.tenant_brand=lark` mid-poll and the credentials come from the Lark hosts, so polling moves there once (`FEISHU_DOMAIN` records which). Pairing writes the four `FEISHU_*` keys, sets `CHANNEL=feishu` unless it already lists feishu, restarts the poller and sends a `paired` message. On a Mac the code is shown by the panel's `--qr` mode (CoreImage `CIQRCodeGenerator`, scaled nearest-neighbour so the modules stay square); Esc there cancels, and a newer `pair-feishu` overwrites `feishu-pair.json`, which the older worker notices and stands down.
- **Sending** goes through `feishuApi` with a tenant token cached per process (one retry on a stale-token code). A blocked ping with options is an interactive card (`feishuCard`), anything else a text message; both are plain text.
- **Receiving** is the long connection, because there is no public URL to deliver events to: `POST /callback/ws/endpoint` with the app credentials returns a `wss://` URL, and every frame on it is protobuf (`pbbp2.Frame`, nine fields), encoded and decoded by hand in `feishu-ws.mjs`. A data frame is acked by sending it back with a `{ code, data }` payload, where `data` is the base64 of the handler's result; a ping goes out every `PingInterval` and silence for a whole interval past it closes the connection for the poller to redial. Split events are reassembled by `message_id`/`sum`/`seq`.
- **`handleFeishuEvent`** returns `{ response, work }` rather than doing the delivery itself: `response` rides back in the ack and must be ready at once (a card tap gets three seconds before Feishu shows an error), `work` is queued on the poller's `serial()`. Only `FEISHU_OPEN_ID` may drive panes, only in a p2p chat, only for this app's `app_id`, and an `event_id` seen before is dropped, because Feishu redelivers what it thinks went unacked and a doubled keypress is not harmless.
- **A text reply** that quotes a ping (`parent_id`) names it and inherits its fingerprint, like a Telegram reply; a bare message goes to the pane of the latest ping. **A card tap** is answered immediately with the card rebuilt without buttons (`1. Yes / sending`), so it cannot be pressed twice; when the delivery finishes, the card is patched to the real ack (`sent · …` or `stale · …`), falling back to a message if the patch fails. A tap on a card missing from `outbound.json` presses nothing.

### Talking to Herdr

All Herdr calls go through `runHerdr()` (`spawnSync` of `HERDR_BIN_PATH` or `herdr`). Herdr's JSON shapes are not stable, so `extractAgentStatus` and `extractReadText` in `src/lib/herdr.mjs` probe several nestings, and `readPaneScreen` tries a list of command variants in order. When adding a new Herdr call, follow the same defensive pattern rather than assuming one shape.

`src/lib/index.mjs` re-exports every lib module; import from it (`../lib/index.mjs`) rather than from individual files.

## Conventions and non-goals

- The plugin id is fixed at `com.codreamer.herdr.oncall`. Do not create `oncall.telegram` / `oncall.app` variants; new channels are a `CHANNEL` value, not a new plugin. `OLD_PLUGIN_IDS` in `paths.mjs` exists only so install can unlink legacy ids.
- Telegram and Feishu messages are plain text, no emoji (tests assert this for both), no Markdown parse mode, no rich-text card elements.
- The location line (`formatWhere`) is `repo · task · space · tab · pane N`, and the desktop panel shows it as its heading with `status · Agent` underneath in small grey — which task it is matters more than what state it is in. The *task* segment is a linked worktree's own directory name (branch appended in parens only when it is not the same slug — `build_deploy_plan` vs `build-deploy-plan` counts as the same), or, for an ordinary checkout, the branch — including `main`, which is as much a fact as any other branch. `resolveWorktree` gets all of it from one `herdr worktree list --workspace <id>` call: `workspace get` only carries a `worktree` block for worktree-backed workspaces, so an ordinary repo used to show nothing but its workspace label. The space segment is dropped when it just repeats the repo or the task.
- Never send the full pane transcript: blocked → dialog tail, done → the last answer only (from the agent's session record, else the screen). On the screen path, `doneSnippet` finds that turn by slicing below the last user marker, and `isUserMarker` cannot tell a sent turn from a prompt box, which is drawn the same way (Claude Code `❯ <whatever is typed>`, Codex `› Ask Codex to do anything`); the structural check above handles a screen with turn markers, and otherwise an empty slice falls back to the tail, because below the box there is only chrome. That mattered once the mode footer stopped being recognised: `⏵⏵ accept edits on (shift+tab to cycle)` was chrome by its key hint, but with monitors or agents attached Claude Code drops the hint (`⏵⏵ accept edits on · 1 monitor · ← 1 agent`) and nothing else matched — a done panel opened with that one footer line as its entire body. The `⏵⏵` marker is what makes it a footer, not what it goes on to say. Codex's footer (`GPT-6-Astra high · ~/repo · branch`, `← for agents · ? for shortcuts …`) is chrome by its shape — a model name, one word, a dot, then a path — and the `? for shortcuts` hint; the effort word is deliberately not listed (one machine said `high`, the next `ultra`). A repainting Codex pane needs this so its box-and-footer read does not settle as an answer.
- Only `TELEGRAM_CHAT_ID` and `FEISHU_OPEN_ID` may drive panes; keep the sender check in both the message and the button path of each channel.
- `CHANNEL` picks where pings go among the *paired* channels (default `telegram`); replies are accepted from every paired channel regardless.
- Scripts that fail exit `0` when the plugin is simply unconfigured or disabled (so Herdr doesn't log noise) and non-zero only for real errors.
