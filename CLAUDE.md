# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A [Herdr](https://github.com/ogulcancelik/herdr-plugin-examples) plugin (`com.codreamer.herdr.oncall`) that pings Telegram or Feishu when an agent pane goes `blocked` or `done`, and delivers replies back into that pane. On macOS a floating desktop panel (`src/desktop/panel.swift`) comes first and the phone channel is the fallback. Plain ESM Node.js (`.mjs`), Node 18+ (22+ for Feishu replies, which need the global `WebSocket`), **no package.json and no npm dependencies** — only `node:` builtins and global `fetch`. The plugin manifest is `herdr-plugin.toml`; bump `version` there for releases — pushing that to `main` is the release (see "Releases and updates" below).

## Commands

```sh
# run all tests (node's built-in runner; `node --test test/` with a bare dir path does NOT work)
node --test 'test/*.test.mjs'

# one file / one test by name
node --test test/pair.test.mjs
node --test --test-name-pattern="pairDeepLink" test/pair.test.mjs
```

There is no lint or build step for the JS. The macOS panel is compiled by `bin/install-deps.sh` (Herdr's `[[build]]` step) with `swiftc` into `bin/oncall-panel` (git-ignored); to rebuild after editing `panel.swift`, run `bash bin/install-deps.sh` (about a minute). It lives in the plugin root rather than the state dir because Herdr sets `HERDR_PLUGIN_STATE_DIR` for events and actions but **not** for build commands, so anything the build writes to "the state dir" lands somewhere the hooks never look. Live testing goes through the Herdr CLI (see README): `herdr plugin action invoke <setup|poll|pair|pair-feishu|unpair-feishu|test|toggle|enable|disable|status> --plugin com.codreamer.herdr.oncall`, then `herdr plugin log list --plugin com.codreamer.herdr.oncall --limit 5` for real output (`action invoke` only returns JSON immediately). `bash install.sh` links the checkout into Herdr for local development.

To exercise the notify hook by hand without pinging Telegram, run it with an empty token and a short delay against a real pane:

```sh
TELEGRAM_BOT_TOKEN= BLOCKED_DELAY_SEC=5 \
HERDR_PLUGIN_EVENT_JSON='{"data":{"pane_id":"wJ:p1","agent_status":"blocked","display_agent":"codex"}}' \
bash bin/run-node.sh src/hooks/notify.mjs
```

## Architecture

### Process model

Every entry point in `herdr-plugin.toml` runs through `bin/run-node.sh`, because Herdr's server does not have a login-shell PATH. The script hunts for `node` (nvm/fnm/mise/volta/homebrew…), caches the path in `<state>/node-path`, and `exec`s it. If something "can't find node", look there first.

Three kinds of process share `src/lib`:

1. **Event hook** — `src/hooks/notify.mjs`. One-shot, spawned by Herdr on `pane.agent_status_changed`. Reads `HERDR_PLUGIN_EVENT_JSON` / `HERDR_PLUGIN_CONTEXT_JSON` from env. Outbound path only.
2. **Poller** — `src/hooks/poll.mjs`. Long-running, detached child (`src/inbound/poller.mjs` spawns it via `spawnDetached` → `run-node.sh`, pid in `<state>/poller.pid`). Runs two loops side by side: the Telegram `getUpdates` long-poll (pairing + replies), and the Feishu long connection (`connectFeishu`, replies + card taps), each idle with a one-line reason while its channel is unpaired. A third loop checks for updates at start and every 6 h (`updateLoop`, see "Releases and updates"). Two more serve drover (see "With drover" below): `escalationLoop` every 30 s and `inboxLoop` every 5 s, both idle while their state file is empty. Deliveries from both chat loops and the inbox go through one `serial()` queue, so two replies never type into panes at once. It is started by `seed.mjs` at build/startup, and `notify.mjs` calls `ensurePoller()` on every event as a self-heal. Any action that touches config calls `restartPoller()`. Its stdout and stderr go to `<state>/poller.log`, timestamped by `withTimestamps()` and rotated once at 256 KB — nothing else captures them, since Herdr's plugin log only sees the action that spawned it and that action exits immediately.
   It rereads `.env` on every pass, so a token filled in after install reaches it without a restart. That rests on two things: `loadDotEnv` never overrides a value the process was *started* with, but a value it read from a file itself follows that file (`setDotEnvValue` marks pairing's write-back the same way); and `startPoller` spawns with `startupEnv()`, the environment minus what the spawner loaded. Handed the hook's loaded values, the poller took them for its own environment, and a fresh install's empty `TELEGRAM_BOT_TOKEN=` stayed pinned until someone ran the `poll` action.
3. **Actions** — `src/actions/*.mjs`. One-shot CLI scripts (setup/install, poll, pair, pair-feishu, unpair-feishu, test, toggle, seed, status). `status.mjs` prints exactly one line of JSON on stdout (contract with drover: version, switch, channels paired or not, poller, panel, drover.env, effective role settings, the main session) and never a secret; drover runs it directly with `run-node.sh`, since `action invoke` returns before any output exists. The fields come from `oncallStatus` in `src/lib/status.mjs`; more may be added, none renamed or dropped. `pair-feishu.mjs` is also the one background worker besides the poller: run as `pair-feishu.mjs wait <device code>` (spawned detached, logging to `poller.log`) it holds the QR panel and waits for the scan, so the action itself returns as soon as the code is printed.

### Two on-disk directories (never confuse them)

- **Config dir** — where `.env` lives. Resolved by `configDirPath()` in `src/lib/paths.mjs`: `HERDR_PLUGIN_CONFIG_DIR` → `herdr plugin config-dir <id>` → XDG fallback. `seedConfigEnv()` copies `.env.example` there and non-destructively upgrades missing keys (`NOTIFY_ON`, `BLOCKED_DELAY_SEC`). `.env` survives reinstalls. `drover.env` beside it is drover's (its installer rewrites it whole, its uninstaller deletes it; Oncall only reads it). `defaultDotEnvPaths()` reads it last, after both `.env` files, and it only fills in: a key some higher layer left empty (`KEY=`, as `.env.example` seeds most of them, or an empty variable in the environment) still takes drover's value, which is the one exception to "first value wins". Between the two `.env` files an empty value still wins, as before. That is also why the drover keys appear in `.env.example` only as comments.
- **State dir** — `stateDir()` in `src/lib/paths.mjs`: `HERDR_PLUGIN_STATE_DIR` → Herdr's own `<state home>/herdr/plugins/<id>` when that directory exists (`herdr-dev` for a debug build) → `<state home>/herdr-oncall` for a machine where Herdr has never linked the plugin. Holds runtime files: `enabled` (toggle), `last-notify.json` (debounce), `blocked-delay.json` (delayed-ping ownership), `outbound.json` (Telegram message_id → pane map, 24h TTL), `telegram-offset`, `poller.pid`, `poller.log` (+ `poller.log.1`), `pair.json`, `feishu-pair.json` (the Feishu scan in progress: device code, page, expiry), `panels.json` (pane → open panel pid), `last-skipped-screen.txt` (the screen behind the most recent `skipped` line, to turn into a fixture), `last-blocked-screen.txt` / `last-done-screen.txt` (the most recent screen a blocked body or a done answer had to be read off because the session gave nothing — written by `saveScreen` in `paths.mjs`, the same idea), `update-check.json` (when the last update check ran), `escalations.json` / `main-inbox.json` / `main-pending.json` (drover only, see "With drover"), `node-path`.

  Herdr sets `HERDR_PLUGIN_STATE_DIR` for events and actions, but **not** for build commands and not for anything you run from a shell — `install.sh` included. Computing Herdr's own path for those cases is not cosmetic: while the fallback was a second directory, a shell-run process and a Herdr-run hook kept separate `poller.pid` files, so `ensurePoller()` could not see the other side's poller. Five of them ended up long-polling one bot token (Telegram allows one, the rest get 409 Conflict), and a stray one that won an update had no `outbound.json` to resolve the pane with, so the reply answered "Reply to a ping so I know which pane." `bin/run-node.sh` is bash and still caches `node-path` under the old path; that one is only a cache, so it re-derives instead of splitting anything.

Tests isolate themselves by pointing these two env vars at `mkdtempSync` dirs; follow that pattern for any new test that touches disk.

### Outbound flow (notify.mjs)

`resolveStatus` → `resolveWorktree` (fills `context.worktree` from `herdr workspace get` and the branch from `herdr worktree list --workspace` when the event did not carry them) → then:

- **done with a menu on screen**: Herdr misses some questions. Claude Code's multi-question form has been reported `done`, and then `idle`, with the form still waiting, and all that opened was a done panel showing the form as text with nothing to press. So a `done` event reads the visible screen first, and when `screenHasOpenMenu` finds an open menu the event is promoted to `blocked` (logged `menu on screen · <where> · herdr said done`) and everything below runs as it would for a real block. The check comes *before* the `NOTIFY_ON` filter, so a setup that only asks for `blocked` still gets these. This is also why `nextDialog` lets only `working` end its wait early: `done` and `idle` are exactly what Herdr keeps saying the whole time such a form is up.
- **blocked, first gate**: read the pane through `readScreenSettled` (up to 6 tries, 500 ms apart, first non-blank read wins) and require `screenHasLiveDialog`. Herdr's `blocked` is not trustworthy on its own — its detector matches dialog wording anywhere in the recent buffer, so an agent that merely *printed* a permission prompt pins its own pane at blocked (this repo did exactly that to itself while building the parser), and `herdr pane get` can also hand back a stale value from the previous detection pass. No live dialog on screen → log `skipped · … · blocked but no dialog on screen · tail: …` (the last 8 non-blank lines) and write the whole screen to `<state>/last-skipped-screen.txt`, so an unrecognised shape becomes a fixture instead of a silent drop. A screen that is still blank after those retries is never evidence of anything: `decideBlockedReal({ screenReadable: false })` is `false` whatever `herdr pane get` says, and the skip reads `blocked but pane screen empty`. Codex clears and redraws the pane the instant a dialog is answered, and trusting the status through that gap is what opened an empty panel with no body and no buttons.
  The exception is an agent whose lifecycle an integration owns (Herdr 0.9.0: Pi, OMP, Kimi Code, OpenCode, Kilo, MastraCode). `agentDetectionSkipped(paneId)` reads `screen_detection_skipped`; when it is true and `stillBlocked()` agrees, `decideBlockedReal` (pure, in `src/lib/herdr.mjs`) calls the block real even with no menu drawn — logged as `hook-authoritative · <where>`. That ping carries no inline keyboard and no fingerprint — and neither does the desktop panel, since both take their buttons from `dialogChoices(screen, { hookAuthoritative })`, the one gate that keeps the `(y/n)` fallback off an agent with no menu drawn — and `paneMovedOn` watches the status instead of the screen. The `agent get` call is made once per hook process, not on every panel poll.

- **blocked, panel available, `BLOCKED_DELAY_SEC` > 0**: `showPanel` replaces the wait. The panel opens on top with its buttons and field but does not take the keyboard (`panelFocus` → `focus: "click"`, which is the binary's default): a question arrives whenever the agent asks it, mostly while the user is typing in some other app, and a panel that activated itself as it appeared caught the rest of their sentence — an Enter in it would even have answered the dialog with option 1. A button answers on the first click; a click anywhere else on the panel activates it and puts the caret in the field, and from there it is the panel as it always was (Enter = option 1, Cmd+N, Esc, Chinese input). The next question of a form waits for a click the same way: no panel takes the keyboard as it opens, and the binary no longer has a way to. A button or typed text goes straight into the pane via `deliverReply`, and then the hook looks for the question that *replaces* the one it just answered: a multi-question form advances tab by tab in place, so Herdr fires no second event and a hook that exited after one answer took the panel with it and left the rest of the form to the terminal. `nextDialog` (`src/lib/format.mjs`) polls until a live dialog with a different `dialogFingerprint` appears, the pane goes back to `working`, or it runs out of tries; `MAX_FORM_ANSWERS` caps the chain. Timeout or Esc falls through to the checks below and then Telegram. While the panel is up, `until` is polled every 2s: the dialog leaving the screen (answered in Herdr) closes it and the hook exits; the user arriving at the pane (`userAtPane`: Herdr focused pane + terminal app frontmost via `lsappinfo`) closes it and the remaining delay runs silently before Telegram. `userAtPane` falls back to the focus flag alone when it cannot identify the frontmost app, and that fallback has one exception it cannot do without: the panel is a bare binary with no `CFBundleIdentifier`, so once it started activating itself for the input method it *became* the unidentifiable app in front, every poll read "the user has arrived", and the panel closed itself two seconds after opening — while the user was still reaching for it. `frontmostApp` returns the display name too, and the panel's own name is never the user at the pane. "The dialog is gone" needs two consecutive polls (`consecutiveGate` in `src/lib/desktop.mjs`) and a blank read counts as neither — one tick can land mid-redraw. The panel is not opened at all when the user is already at the pane. A newer blocked event for the same pane kills the older panel (`panels.json`) and the older hook exits as `superseded` — but only a *question* may evict a question: `panelOutranks` keeps a `done` panel from taking a blocked panel's place, which used to make the question disappear without even reaching Telegram, since Claude Code emits both for one pane inside a second.
- **blocked, after the wait**: re-read the pane with `readScreenSettled` and require a live dialog again (not `herdr pane get`), plus `blockedDelayStillMine`.
- **blocked again for the same call** (`alreadyShown`): Herdr can report `blocked` a second time for a dialog that never went away (the main session's one WebFetch call got two cards 35 s apart). When the dialog's call (see "Inbound flow") already has a panel open for it (`panels.json` keeps the panel's `callId`), the hook exits (`not sent · … · a panel for this call is already open`); when it has a card that can still be pressed (same pane and call, not `spent`, call still open), no card goes out (`not sent · … · already pinged for this call`) and the phone is not pinged after the panel's wait either. A spent card does not count, so a dialog whose card was refused or replaced is pinged again. A form and a dialog with no call are never deduplicated.
- Chat ping (`pingRemote`, once per event, to every channel in `remoteChannels()` — the paired ones `CHANNEL` selects — each in its own try so one being down does not cost the other its ping, via `pingChannels` in `channels.mjs`): `shouldDebounce` → `readPaneScreen` (`herdr pane read`; `recent-unwrapped` source for done, `visible` for blocked) → `blockedSnippet`/`doneSnippet` + `parseBlockedOptions` (`src/lib/format.mjs`) → `sendRemote` (Telegram: inline keyboard for blocked options, else force-reply; Feishu: a schema 2.0 card with one button per option, else a text message) → `rememberOutbound(messageId → pane)`, which also stores the dialog's `fingerprint`, parsed `options`, the `channel`, and for a Feishu card its `text`, so the card can be rebuilt after a tap.
- **Every ending says why.** A colleague's Codex blocked pings stopped reaching Feishu while `test` still did, and the plugin log could not tell the possible causes apart: the toggle being off, `NOTIFY_ON`, a debounce, a dialog answered during the wait, a newer event taking over, and a ping that *was* sent all left the same empty line. Now each one prints a line for blocked and done events: `off · …` / `ignored · …` (`eventGate` in `gate.mjs`, silent for working/idle, which arrive every turn), `debounced · …`, `not sent · <where> · <reason>` (`blockedWaitVerdict` after the wait; no paired channel in `CHANNEL`; a newer event took the panel over), and `sent · <channel> · <where>` on success (`pingChannels`). The README has the table. Keep it that way when adding an exit to `notify.mjs`: an exit that prints nothing is a bug report nobody can answer. Relatedly, `test` (and the seed/install hints, via `modeHint` in `setup.mjs`) says when Oncall is toggled off, because `test` sends its ping regardless and was the one thing still working.
- **Blocked body from the session** (`blockedBody` in `notify.mjs`, `sessionDialogBody` in `src/lib/transcript.mjs`): a permission dialog is about a tool call the agent already made, and the session records that call the moment the model emits it — its result only once the user answers (a real Claude Bash approval: called 03:11:41, answered 03:13:00). So the open call is the dialog's subject, whole, where the screen cut the command at the pane width. **Claude Code**: `claudePendingCalls` takes the current turn's `tool_use` blocks with no `tool_result` (none once `end_turn` is last; a user prompt is where the turn began). **Codex**: `codexPendingCalls` takes the calls since the last `task_started` with no `*_output` for their `call_id` (none after a `task_complete`); Codex writes no approval events, only the calls. `describeCall` renders each per tool — Bash command and description, Edit/Write path and lines, WebFetch URL, AskUserQuestion / Codex `request_user_input_async` one candidate per question with every option's description, an MCP tool's input — and names a `witness`, the piece of it the screen must show. Any other tool gives nothing: a bare tool name is too weak a witness — the `Agent` call that started a foreground subagent stays open while it runs, and "agent" is on the screen of every dialog that subagent raises. `pendingDialog` uses the first candidate whose witness (whitespace, Markdown marks and box-drawing characters removed — Claude draws a `│` gutter down a quoted command — first 40 chars, at least 4) is on screen: a turn can have several calls open (Claude runs tools in parallel) and the dialog asks about one, and a dialog that is not about a call at all (Claude's "Teach auto mode…", a folder-trust prompt) matches nothing. **A subagent's calls are not in the session's transcript** but in its own, `<session>/subagents/agent-<id>.jsonl`, every record `isSidechain`, with its `agentType` in the `.meta.json` beside it; `sessionDialogBody` reads the session's first, then the 8 most recently written subagent transcripts (the last 1 MB of each), and a body found there is headed `… · from the <agentType> agent`, as the dialog itself says. Before this, a dialog a background subagent raised went out without its command. No match, no session, or Codex's code-mode `exec` (its input is JS that calls `tools.exec_command`, so the approved command is buried in code) → `blockedSnippet` as before, and that screen is saved to `last-blocked-screen.txt`. The screen's question line (`dialogQuestion`) goes under it, except for a form, whose candidate is the question. **The choices, the keys, liveness and the fingerprint never come from the session** — they are what a reply presses, and the screen is what it presses on. The poller's `followForm` builds a form's next question the same way. The plugin log says `blocked · <where> · body from session|screen`, once per distinct screen.
- **done**: the chat channel is pinged first, then the panel opens with the last answer, passively (`panelFocus` → `focus: "never"` → the binary's `--passive`): no text field, the ordinary window level, and it never activates or takes the keyboard. It used to carry a text field and activate itself as it opened, and a turn tends to end while the user is typing in some other app — the rest of their sentence landed in the done panel's field and would have gone to the pane as a prompt. A finished turn needs reading, not answering; a follow-up goes in from the pane itself or as a reply to the phone ping. **The answer comes from the agent's own session record, not the screen** (`sessionAnswer`, `src/lib/transcript.mjs`). Reading it off the screen meant guessing which lines were the answer and which were whatever the agent draws around it, and every new footer an agent grew went out as the ping — Codex's `› Ask Codex to do anything` prompt box reads exactly like a sent turn, and the model line and shortcut hints under it made a ping that was nothing but footer. Getting from a pane to its session (`paneSession`) asks nothing of the user. First, the session Herdr's integration reported on `SessionStart` via `pane.report_agent_session`, which `agent get` returns as `agent_session: { agent, kind: "id"|"path", value }`. Failing that, for **Claude Code**, its own per-process record: `herdr pane process-info --pane <id>` names the pane's process group leader and foreground pids, and `~/.claude/sessions/<pid>.json` (`CLAUDE_CONFIG_DIR`) holds that process's current `sessionId` (it follows `/clear` and resume; a `kind` other than `interactive` is a one-shot `claude -p` and is skipped). That is exact and covers sessions started before Oncall was installed; a session with no message yet has a record but no transcript file, and needs none. **Codex** keeps no per-process record — its terminal hands the session to a background server, which holds every thread's writer lock — so a Codex pane is tied to its session only by Herdr's Codex integration, and `ensureIntegrations` installs it (`herdr integration install codex`) from `seed.mjs` on every build and Herdr start, from `install.mjs`, and from the done hook when a Codex pane has no session to find — Codex installed after Oncall would otherwise wait for the next Herdr start, and Herdr's server can run for days — whenever `~/.codex` exists and `herdr integration status` does not say `current`/`installed`. `INSTALL_AGENT_INTEGRATION=0` turns that off. The integration writes a hook into Codex's config; Codex asks once to trust it, and only sessions started afterwards report. Claude Code's integration is never installed by Oncall: it is not needed. Claude Code reports the id and its transcript path; Codex only the id, found as `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl` (a fork is `…-<parent>_<id>.jsonl`, so the match is on the ending). From the file's tail: **Codex**'s answer is the last `event_msg` `task_complete`'s `last_agent_message`, and a `task_started` after it means the turn is not written yet; **Claude Code** writes each content block as its own record, every block of the turn-ending message carries `stop_reason: "end_turn"`, so the answer is the text in that trailing run (narration before a tool call ends in `tool_use` and stays out; `isSidechain` subagent records are skipped). A done event can land a moment before the file has the turn, so an unfinished file is re-read (6 tries, 500 ms apart) — and never answered with the previous turn's message. A long answer keeps its beginning (`capAnswer`). The plugin log says `done · <where> · answer from session|screen`. The screen is used for a pane whose session cannot be found — any agent other than Claude Code and Codex, or a Codex session started before the integration was installed.

  The screen is the fallback, for any pane whose session cannot be found. That read is settled too, but on a different condition: a done event lands the instant the turn ends, which is also when the agent repaints, and it repaints from the bottom — the prompt box, the rules and the mode footer are on screen before the turn above them. That read is not blank, so the gate `blocked` uses would hand it straight back and the ping would carry nothing. `readScreenSettled`'s `ready` predicate takes `doneSnippet(text)` being non-empty instead, so it waits for a read with a turn in it. `doneSnippet` tells the prompt box from a sent turn structurally where it can: when the agent's turns are on screen (`isTurnStart`: `⏺`/`●`, or Codex's `•` at the left edge), a user line with no turn after it is the box, so the answer runs from the user line before it up to the box.

The panel binary speaks a one-line stdout protocol (`button:<i>` / `text:<t>` / `timeout` / `dismiss`), parsed by `parsePanelResult` in `src/lib/desktop.mjs`. Panel debounce uses the keys `panel:blocked` / `panel:done` so it does not interfere with the Telegram debounce. **No panel takes the keyboard as it opens** — not a question, not a done report, not the `test` action's or the pairing panels — because panels appear when an agent gets somewhere, mostly while the user is typing in another app. The binary has no path that does it, so no caller can ask for it or forget not to. Its `focus` (`showPanel({ focus })`, chosen for the hook's panels by `panelFocus`) is `click`, the default, which floats and takes the keyboard once clicked, or `never` (`--passive`, a done panel). Taking the keyboard always means `NSApp.activate`, not just becoming key: an input method attaches to the *active application*, not to whichever window holds the caret, so as a `.nonactivatingPanel` the field took raw keystrokes (fine for `y` or `1`) while the IME stayed with the terminal and Chinese could not be typed at all. Activating makes macOS write input-method chatter to stderr, which `panelStderr` drops so a working panel does not log two errors per notification. Opening *without* taking the keyboard needed more than not calling `activate`, twice over, and each has its own guard: as an `.accessory` app the panel was handed activation at launch whenever the frontmost app was the terminal it descends from (`didBecomeActive` 0.05 s in, `lsappinfo front` on the panel), so every panel starts background-only (`.prohibited`), which macOS never activates; and as a `.nonactivatingPanel` that could become key, AppKit made it key the moment launching finished, so `canBecomeKey` is false until the panel may take the keyboard. Every panel is shown once with `orderFrontRegardless()`. A `click` panel looks at mouse-downs in `PanelWindow.sendEvent` (`interceptMouseDown`): one on a button goes straight through and answers; the first one anywhere else switches the process to `.accessory`, lets the window become key, activates, makes the field first responder (a QR panel has none, but Esc reaches it now and cancels the pairing), and is consumed (on the body it would hand the caret to the read-only text); a later one re-activates if the user clicked away in between, since a `.nonactivatingPanel` gets key status back from a click but not activation. Until that click the field's placeholder says to click. A `never` panel stays background-only and never key (Esc does not reach it; the close button does), and sits at `.normal` level with `isFloatingPanel` off — set explicitly, since an NSPanel with `.utilityWindow` comes out floating (level 3) by default — so it lands over the window in front and the next click on that window covers it; every other panel floats. `DESKTOP_PANEL_DEBUG=1` prints the panel's focus mode, level, key and active state and its first responder half a second after it opens (launching hands out activation and key status only once the run loop is going), and again after the focusing click; that is the line to check when changing any of this, with no other `oncall-panel` running — a live one that has been clicked into skews the reading.

### Reading a permission dialog off the screen (`src/lib/format.mjs`)

`screenLines` keeps blank lines and drawn rules — they are the block boundaries, and the old version that filtered them out is what forced guesswork like "take the last N lines". `dialogRegion` then locates the dialog structurally, and both `blockedSnippet` and `parseBlockedOptions` work from that one region:

- **options**: the run of numbered lines at the *bottom* of the screen, found by skipping the trailing key hints and walking up. Taking the first numbered run below the question instead is what once put a workflow's phase list (`1. Review — three lenses…`) on the buttons and dropped the real `1. Yes, run it` as a duplicate index. A more indented non-numbered line inside the run is a wrapped option, and `joinWrappedOptions` puts it back on the label before parsing, so a choice the terminal broke in two is weighed exactly like the same choice on one line — `(esc)` becomes the send key either way, `(shift+tab)` stays prose either way, and the label stops moving when the pane is resized. A tail hanging off the *last* option is the first thing the scan up from the bottom meets, so it is stepped over rather than read as the end of the dialog — but only one that hangs deeper than its option: at or left of the option column, a line ending in `(y)` is content under the list, not part of it. A form's choices put a description on the lines under them, at the very same hanging indent, and joining those on is what put `1. Drop it (Recommended) A failed send gets Home's per-message r` on a Telegram button. Indentation cannot tell the two apart, but width can: a word moves down only when it does not fit, so after a real wrap the line above, a space and the carried word together overrun the pane (`wrappedOnto`, with the pane width taken from the widest line on screen — the rules run the full width — and CJK counted as two columns). The label is the numbered line plus what wrapped off it; from the first line that did not wrap, the rest is description, which stays in the snippet body but never on a button. Labels are cut at 96, the width of the panel button (`panelLabels`); Telegram caps its own at 64. A drawn rule inside the run is crossed only when the line above it continues the numbering downward — Claude Code's tabbed multi-question form puts `4. Chat about this` in its own section under a divider, and stopping at that rule left exactly one useless button.
- **question**: the nearest line above the run that ends in `?` or the fullwidth `？`, stopping at the same structural boundaries as the body walk. Only when there is no numbered run at all (a bare y/n prompt) does it fall back to matching wording (`would you like` / `do you want` / `allow` / `permission`), which is still English-only.
- **start**: if non-blank content sits between the question and the first option, the command is *below* the question (one Codex shape) and the question is the start. Otherwise the content is *above* (Claude Code, Codex "requires approval") and the walk goes up to the first structural boundary: a turn marker (`⏺`/`●`, included — it names the tool), a Codex tool header line, the previous user turn, a drawn rule, or two consecutive blanks. There is deliberately **no line cap**: the input is a single viewport, so the walk is already bounded, and a cap only truncates long commands.
- **render**: `renderBlock` drops rules, trims the edges, and collapses blank runs.
- **shortcuts**: a trailing parenthetical becomes the key to send only when it names one — a single letter or digit, or `esc`/`escape`/`enter`/`return`/`tab`/`space`. Anything else (`(default)`, `(shift+tab)`) stays in the label and the option index is sent instead; the old "alphanumeric and ≤ 8 chars" rule made `1. Yes (default)` type the word `default` into the pane.
- **fingerprint**: `dialogFingerprint` hashes the question, every `key|<option's whole text>`, and the rendered body *above* the first option into 16 hex chars — the body is in there because two Bash approvals in a row ask the identical question with the identical choices and only the command differs, and the option lines are left out of it because they are already hashed per option, so moving the terminal's `❯` marker between choices (or re-wrapping them) must not invalidate a ping. Each option is hashed as its whole text, description included, rather than its button label: where the label ends is judged against a width read off the screen, and a hash must not move with that reading. A choice with no description has the same text either way, so those fingerprints are what they always were. It is what the inbound path compares against the live screen before pressing a key when there is no tool call to go by, and hashing only the region is what keeps it stable while a spinner or footer changes underneath. It is not stable across widths: a question that re-wraps when the pane is narrowed (measured on Claude Code's WebFetch dialog at about 35 columns: `Do you want to allow Claude to` / `fetch this content?`) hashes differently, and a real tap on the main session's still-unanswered WebFetch dialog was refused that way, leaving a dead card. Hence the call identity below.
- **liveness**: `screenHasLiveDialog` says a dialog is *waiting* rather than merely *quoted* — only blanks, drawn rules and chrome may follow it. Getting `isRuleLine` and `isChromeLine` right matters here: the labelled separators the agents draw (`──── ultracode ↯ ─`), the status footers (`➜ repo git:(main) ctx:33% Opus 5`, `» Ask Codex…`) and Claude Code's task list (`4 tasks (3 done, 1 in progress, 0 open)` and its `✔`/`◼`/`◻` rows) all sit under a real dialog, and treating them as content swallows genuine notifications. The task list cost every pane with a todo the panel *and* its buttons, silently, until the skip trace caught it: both liveness and `trailingOptionRun` find the dialog by walking up from the bottom past the chrome, so one unrecognised footer breaks both.

  The error runs the other way too, and is worse: chrome rules that are too *loose* eat real content. `tokens?` matched any short line mentioning the word, so an option whose description read `任何人可从 ai-assistant 取到 ASR token` ended the walk and the ping went out with the first two choices missing. A footer's token count is what makes it a footer, so the rule requires the number. `shift+tab` was the same trap one level down: a long option (`2. Yes, and always allow access to /Users/… for this session (shift+tab)`) wraps past the pane width and leaves its parenthetical on the next line, where the key-hint rule claimed it — the walk stopped there, the panel opened with one button (`3. No`), and the other two choices were stranded in a body that began at the question instead of the turn marker. It happened twice, because the first fix spared only a line that was *nothing but* `(shift+tab)`; with a longer path the wrap carries the word before it too, and `session (shift+tab)` was a footer again. A real key hint says what the key *does* (`shift+tab to cycle`), so its parentheses never hold a bare key, and a line that *ends* in a bare key name in parentheses is never chrome (`endsInKeyParenthetical`).

  Narrow panes break the hints too, the other way. Codex sets its hints as `<key> to <what it does>` items joined by ` | ` (`tab to add notes | enter to submit answer | ←/→ to navigate questions | esc to interrupt`, about 90 columns for a multi-question form, sometimes after an `option 4/5` position) and wraps them between items, so any Herdr split narrower than that left `tab to add notes | enter to submit answer` alone on a line, without the `esc to` that made the whole line chrome. The form read as quoted, and the ping was skipped. `isKeyTipLine` recognises such a line: every ` | ` item names a key and then `to …` (the key list is in `HINT_KEY`, so prose that says "to submit" is not taken). The approval's own `Press enter to confirm or esc to cancel` (43 columns with its indent) breaks after `to` and leaves `cancel` on its own line. Both shapes come from openai/codex's own TUI snapshots (`request_user_input` footer_wrap, `approval_overlay` clipping_tests).

  Neither is a chrome rule, because a choice's description reads the same: `Return to the previous screen` under `2. Go back`. The first version put `isKeyTipLine` in `isChromeLine`, and that cut the choice list at the description, leaving only `3.`, with no open menu while the cursor sat on 1 or 2. They live in `isFooterAt(lines, i)`, which only the two trailing walks use (`screenHasLiveDialog` after the region, `trailingOptionRun` from the bottom up). It requires the line to sit no deeper than the last choice's *number* (`atFooterColumn`; footers are drawn at the dialog's margin, descriptions hang deeper). A hint line also has to be in a block of its own (`inFooterBlock`: a blank line or rule above it, nothing in it but hints and chrome). A wrapped tail (`cancel`) has to sit right under a footer line that ends on `to`/`or`/`and`. Separately, the walk *up* a choice list no longer stops at a chrome-looking line that hangs under a choice (`hangsUnderOption`). `Esc to abandon the change` as a description used to cut the list through the global `esc to` rule, before any of this. The regression test pins the Return/Tab/Enter shapes to the fingerprints the code had before the footer rule existed.
- **open menu**: `screenHasOpenMenu` is stricter than liveness, and it is the only screen check allowed to overrule Herdr's status (promoting a `done`, or retyping a reply). Liveness alone cannot make that call: when a turn ends on a numbered list, only the empty prompt box and its footer sit below it, which is exactly what sits under a real dialog. A list in prose never has the selection cursor, though, so an open menu also needs `❯`/`›`/`▸` on one of its choices, plus at least two choices so that a numbered draft typed into the prompt box (`❯ 1. now bump…`) does not qualify.

Reading the pane goes through Herdr's socket to the server that owns the PTY, so it works regardless of what is on the physical display — the terminal can be minimised, on another Space, or in an unfocused workspace. Only `userAtPane` (which suppresses the panel) depends on the desktop.

When a dialog shape does not extract cleanly, capture the real screen and add it as a test case rather than tuning a threshold. It is usually already captured: any ping whose body or answer came off the screen left that screen in `<state>/last-blocked-screen.txt` or `last-done-screen.txt` (a skip, in `last-skipped-screen.txt`), and the plugin log line says `from screen`. A dialog is gone by the time someone reports it, so that file is the fixture; otherwise `herdr pane read <pane> --source visible --format text` while it is still up. Claude Code's newer permission dialog draws dashed rules (`╌`) above and below the command, and the screen walk stops at the first rule it meets going up from the question, so its screen body loses the command — fix that from a captured screen, not a guess at the glyph.

### Inbound flow (reply.mjs)

With `MAIN_AGENT_NAME` set, a text message goes through `routeChatMessage` first (see "With drover" below); this is still the path it takes to answer a quoted dialog, and the one for `BARE_MESSAGE_TARGET=last`.

`handleTelegramUpdate` → pairing check (`/start CODE` or bare code while `pair.json` is pending; writes `TELEGRAM_CHAT_ID` via `upsertEnvValue`) → reject any chat other than `TELEGRAM_CHAT_ID` → `resolveReplyTarget` (the `reply_to_message` id looked up in `outbound.json`, else the most recent outbound, and the record is tagged `explicit` when the reply named it) → `deliverReply`, which re-reads the **live** pane status and classifies:

| live status | reply text | herdr command |
|---|---|---|
| blocked | single key / named key (`y`, `esc`, `enter`…) | `pane send-keys` |
| blocked | anything else | `pane send-text` + `send-keys enter` |
| other | anything | `agent prompt` (falls back to send-text on `agent_blocked`) |

The live status is `pane get`'s, with one override: when Herdr says anything but `blocked` while an open menu is on screen (`screenHasOpenMenu`), `deliveryStatus` treats the pane as blocked. `agent prompt` *submits* — it types the text and presses Enter — so on a form Herdr calls `idle`, a `1` picks the first choice, the form moves on to its next tab, and the Enter answers that tab too.

Before any of that, a reply that names its ping is re-verified (`staleDialog`): `deliverReply` reads the screen again — **whatever `pane get` says**, because Herdr's status lags and a pane it still calls `working` can already have the next dialog drawn on it. A Telegram button lives forever, the dialog it belonged to does not, and a `1` meant for one prompt must not land on the next one. **The tool call decides first.** Every blocked ping (card, panel, escalation) records the call its dialog is about when the session has it (`sessionDialog` → `call: { agent, file, id, name, asks, sidechain }`; the session or subagent transcript and the `tool_use` id, Codex's `call_id`), and `callState(call)` reads that file: no result yet is `open` (the dialog has not been answered: same dialog, whatever the screen's fingerprint now), a result is `answered`. Open with a live dialog or open menu up, and the dialog on screen is that call's (or names no call): press. Open but the screen shows another call's dialog (one approved and still running, another asking), answered, or open with no dialog left: stale. A form (`asks`: AskUserQuestion, request_user_input) asks every question under one call, so it, and anything with no call (no session, Codex's code-mode exec, a folder-trust prompt) or an unreadable record (`unknown`), still goes by `dialogFingerprint`. A pane that cannot be read at all logs `fingerprint unverified · <paneId>` and sends anyway. Which replies are checked is `replyFingerprint(target)` / `target.explicit`: only ones that named their ping — an explicit `reply_to_message` or a button tap — since a **bare** message that merely resolves to the most recent outbound is about the *pane*, not about that dialog, and must still deliver as a prompt. The ping's own status gates it too, so a done record is never checked. The `agent prompt` → `agent_blocked` fallback runs the same check a second time.

**No dead cards** (`answerStale`). A refused reply returns `{ stale: true, reason, screen }` and nothing reaches the pane, but the user must still have something to press. The card that was tapped is marked `spent` in `outbound.json`. `reason: "changed"` (a dialog is up, not that one or not tellable): a new card for the dialog on screen goes out at once (its own buttons, fingerprint and call, the old card's title / layout), and the old card says `弹框变了，没按 · <where>` / `已换成下面这张新卡片` (said first, so on Telegram it sits above the new card); if that dialog already has a card that can be pressed, the old one points there instead. `reason: "gone"` (no dialog left): `这个确认已经处理过了 · <where>`, the one case where nothing to press is right. A tap that lands marks its card `spent: "sent"`. The desktop panel does the same: a click that did not land reopens the panel on the dialog that is up now (`followPanel`), and only a dialog gone closes it.

Inline-keyboard taps arrive as `callback_query` and take the same `finishDelivery` path; a tap always names its own message, so an id missing from `outbound.json` is acked with `no pane mapped for that button` rather than falling back to the most recent ping. `handleTelegramUpdate` takes its Telegram and Herdr edges (`send`, `answer`, `run`, and `wait` for `nextDialog`) from its `deps` argument, defaulting to the real ones, so the whole inbound path is testable without a network or a live pane.

A reply to a blocked ping that lands in a live dialog is followed, the same way the panel follows a form (`followForm`): the Telegram ping goes out just as its hook exits, so nothing else is left to notice that the form moved to its next tab, and answering the first question from Telegram used to leave the rest of the form sitting in the terminal. `finishDelivery` reads the dialog's fingerprint *before* delivering the reply, and afterwards runs `nextDialog` against it. When a different question appears, it is pinged like any other — its own buttons and fingerprint, stored in `outbound.json` under the first ping's `title` (which `rememberOutbound` keeps for this reason) and `where` — so it can be answered and followed in turn. This blocks the update loop for as long as `nextDialog` waits (up to 8 s; a one-off dialog ends at the first read where the agent is `working`). A follow-on ping that fails to send is logged as `follow-on ping failed · <where>: …`, and the answer that already went through still counts as delivered.

`finishDelivery` and `followForm` do not know which chat they are in: they talk to a channel object (`{ name, reply(text), ping(text, { options }) }`), `telegramChannel(deps)` in `reply.mjs` or `feishuChannel` in `inbound/feishu.mjs`, and a follow-on question goes out on the channel the answer came from. `deps.ack` overrides only the ack, which is how a Feishu card reports on itself.

### Feishu (`src/lib/feishu.mjs`, `src/lib/feishu-ws.mjs`, `src/inbound/feishu.mjs`)

- **Pairing is app registration.** `pair-feishu` calls Feishu's device-flow registration (`accounts.feishu.cn/oauth/v1/app/registration`, `action=begin`, `archetype=PersonalAgent`, the same protocol `lark-cli config init --new` and the official OpenClaw installer use): it returns a device code and a page to scan. Polling that code (`feishuRegistrationWait`) ends with a newly created bot app's `client_id`/`client_secret` and the scanner's `open_id`, so one scan is both the bot setup and the pairing — there is no token to paste. A Lark tenant reports `user_info.tenant_brand=lark` mid-poll and the credentials come from the Lark hosts, so polling moves there once (`FEISHU_DOMAIN` records which). Pairing writes the four `FEISHU_*` keys, sets `CHANNEL=feishu` unless it already lists feishu, restarts the poller and sends a `paired` message. On a Mac the code is shown by the panel's `--qr` mode (CoreImage `CIQRCodeGenerator`, scaled nearest-neighbour so the modules stay square); the close button, or Esc once the panel has been clicked (it takes the keyboard on a click like every panel), cancels, and a newer `pair-feishu` overwrites `feishu-pair.json`, which the older worker notices and stands down.
- **Pairing twice is not pairing again.** Every registration creates a bot, and Feishu has no way to hand it an existing one, so a colleague who reinstalled and scanned again ended up with a second bot. The `.env` had never gone anywhere: Herdr keys the config dir by plugin id alone (`plugin_config_dir`), and neither `plugin uninstall` nor install/update (including the move onto `--ref stable`) touches it. So `startFeishuPairing` (`src/lib/feishu-pairing.mjs`) runs before `begin`. With all three of `FEISHU_APP_ID`/`FEISHU_APP_SECRET`/`FEISHU_OPEN_ID` set it asks Feishu for a fresh tenant token (`feishuVerifyCreds`). If Feishu takes it, the machine is already paired: nothing is registered, the bot is messaged `already paired`, the log and the panel say so and point at `unpair-feishu`, and a `CHANNEL` without feishu is set to feishu as a first pairing would. A new bot is registered only when Feishu says this app is dead, and that is a whitelist (`DEAD_APP_CODES`): 10014 app unauthorized (disabled) and 10015 wrong app secret, the two rows about the app's own state in the platform's 服务端错误码说明, which the token endpoint's page names as its error-code reference. Every other answer keeps the pairing and creates nothing (exit 1). The first version took any non-zero code for a refusal, and 21001, an access-control policy that this endpoint returns as HTTP 200 and that clears up by itself (larksuite/openclaw-lark#639), would have sent a working machine to scan again. Don't widen the list on a guess; one wrong code there recreates the bug. `unpair-feishu` (`unpairFeishu`) is the one way to start over. It first withdraws any scan in progress (`cancelFeishuPair` removes `feishu-pair.json`, so the waiting worker's `wanted` check stands it down), messages the old bot `unpaired` (best effort), empties the four `FEISHU_*` keys (emptied, not deleted, as `.env.example` ships them), takes feishu out of `CHANNEL` (`telegram` when nothing is left, which is what an empty `CHANNEL` means), restarts the poller, and says that the old bot is still in Feishu to delete by hand. The worker asks once more right before it writes an approved scan (`saveFeishuPairing`, by `feishuPairId`, which ignores expiry), because the scan can be withdrawn after Feishu approved it and before the write; a withdrawn result is not saved, and the app it created is named for deleting. These functions take every edge (verify, begin, send, panel, `.env` writes, the scan record, the poller) through their argument, so `test/pair.test.mjs` runs them with no network and no bot.
- **Sending** goes through `feishuApi` with a tenant token cached per process (one retry on a stale-token code). A blocked ping with options is an interactive card (`feishuCard`), anything else a text message; both are plain text.
- **Receiving** is the long connection, because there is no public URL to deliver events to: `POST /callback/ws/endpoint` with the app credentials returns a `wss://` URL, and every frame on it is protobuf (`pbbp2.Frame`, nine fields), encoded and decoded by hand in `feishu-ws.mjs`. A data frame is acked by sending it back with a `{ code, data }` payload, where `data` is the base64 of the handler's result; a ping goes out every `PingInterval` and silence for a whole interval past it closes the connection for the poller to redial. Split events are reassembled by `message_id`/`sum`/`seq`.
- **`handleFeishuEvent`** returns `{ response, work }` rather than doing the delivery itself: `response` rides back in the ack and must be ready at once (a card tap gets three seconds before Feishu shows an error), `work` is queued on the poller's `serial()`. Only `FEISHU_OPEN_ID` may drive panes, only in a p2p chat, only for this app's `app_id`, and an `event_id` seen before is dropped, because Feishu redelivers what it thinks went unacked and a doubled keypress is not harmless.
- **A text reply** that quotes a ping (`parent_id`) names it and inherits its fingerprint, like a Telegram reply; a bare message goes to the pane of the latest ping. **A card tap** is answered immediately with the card rebuilt without buttons (`1. Yes / sending`), so it cannot be pressed twice; when the delivery finishes, the card is patched to the real ack (`sent · …`, `弹框变了，没按 …` with a new card below, or `这个确认已经处理过了 …`), falling back to a message if the patch fails. A tap on a card missing from `outbound.json` presses nothing.

### With drover: roles, escalation, the main session's inbox (`src/lib/roles.mjs`, `src/inbound/escalation.mjs`, `src/inbound/main-inbox.mjs`)

drover runs a main session (the agent named `MAIN_AGENT_NAME`, registered by drover as `drover`), orchestrators (`SUPERVISOR_PREFIX`, `orch-`) and workers (any other named agent). Each layer approves the dialogs of the one below, so only the main session's dialogs are the user's. The cross-repo contract (the main session's name, `drover.env` and its keys, the status fields, the chat prefixes) is agreed with drover, whose installer and `drover oncall` commands depend on it; change it only together with drover. **Everything here is off while `MAIN_AGENT_NAME` is empty**, and that has to stay byte-for-byte 0.6.6: `paneRole()` asks Herdr nothing then, the chat handlers take their old branch before any new code runs, and the tests pin both.

- **Roles in the hook.** `paneRole(paneId)` makes the hook's one `agent get` and classifies the name (`classifyRole`; `extractAgentLabel` reads `name`, which is not `extractAgentName`'s kind). It sits after `eventGate` and `where`, before the blocked and done handling. `notifyPlan({ role, status })` is the pure decision the tests walk row by row. Orchestrator / worker done: `quiet · <role> · <name> · <where> · done (supervised)`, nothing else. Their blocked: the same live-dialog gate as always, then `armEscalation` writes `{ paneId, role, name, kind, where, fingerprint, startedAt }` to `escalations.json` and the hook exits (`escalation armed · …`; the same fingerprint again keeps its `startedAt`, `escalation kept · …`). No panel, no ping, no sleeping hook.
- **Escalation in the poller.** `checkEscalations` (every 30 s) rereads each armed pane: blank is never evidence (unless `pane get` says `pane_not_found`), no live dialog is read once more a second later and then cleared, a different dialog resets the clock, the same one past `escalateAfterSec` (orchestrator `SUPERVISOR_ESCALATE_SEC`, or `_CODEX` when the main session's kind is codex; worker `SUPERVISED_ESCALATE_SEC`) is pinged once: `escalatedAt` is written before the send. "The same dialog" goes by the record's `call` when it has one (the hook arms with it): still open and the screen's dialog not another call's is the same, however the screen is redrawn (an orchestrator's clock kept restarting on fingerprint changes, so it might never come due); answered is a different dialog, re-armed with the call now on screen. Without a call, the fingerprint. A dialog on screen also needs Herdr not to say `working` (`observe`): a worker that printed approval text of its own (it was reading a session record) ended its output on a question and numbered choices with only its spinner below, `screenHasLiveDialog` took that for a dialog, and the live poller reset the worker's clock twice while Herdr rightly said working; ten minutes of it would have sent an escalation for nothing. `done` / `idle` with a dialog drawn is Herdr missing one and still counts, as does an unreadable status; the hook only arms on `blocked`, so a background subagent's dialog that Herdr reports as working was never in scope. The ping (`escalationText`: `升级 · worker <name> 卡在确认框 N 分钟`, where, who normally approves, the body from the session or the screen, `BLOCKED_HINT`) goes through `pingChannels` with options and fingerprint and is remembered in `outbound.json` like any blocked ping, so buttons and the stale check work unchanged. No phone channel: the panel. Toggled off: held, not marked. Every write goes through `settle()`, which re-reads the file and applies the change only while the record is still the one looked at, because the hook can arm a newer dialog while a ping is in flight.
- **Main session, done** (`mainDone` in the hook → `mainDonePings` / `sendMainPings` in `main-inbox.mjs` → `mainDonePlan` in `roles.mjs`). The chat is for approvals and instructions, not for relaying every turn (the user's call), so with `MAIN_DONE_PING=relay` (drover's setting; `always`, the default, is every turn) a done sends only: the answer to each chat message still waiting for one, as a reply under it; this turn when its closing answer (`sessionAnswer`, the end_turn text run, not narration before a tool call) starts with `MAIN_RELAY_MARKER` after leading blanks, marker kept; an API error notice. Nothing else: `quiet · main · <where> · done (not a chat answer or relay)`, and the passive panel opens as before. The same text never goes out twice. With roles active these pings are bare text (no `done · Claude`, no location line), and the main session's dialog is headed `主会话在等你确认` with no location line (`mainBlockedText`; `layout: "main"` in `outbound.json` so a form's next question in `followForm` looks the same). Escalations keep their location line. The API error check comes first: the visible screen through `apiErrorLine`, a port of drover's `api_error()` (`CLAUDE_API_ERROR_RE`, `CODEX_API_ERROR_RE`, `OUTPUT_BLOCK_RE`: an error line at the start of a line that is the last output block).
- **The chat as a line to the main session.** With roles active, `onMessage` (Feishu) and `handleTelegramUpdate` hand every text to `routeChatMessage`: commands first (`/help` `/off` `/on` `/send`; any other `/x` is answered as unknown, never typed), then the off switch (off means nothing from the chat reaches a pane: messages, quotes and card taps alike), then a quoted ping (a blocked one answers its dialog through `finishDelivery` as always; a non-blocked one on the main pane is a prompt), then a bare message (`BARE_MESSAGE_TARGET=main` → `routeToMain`, else the latest ping as before). Anything that reaches the main session as a prompt goes through `routeToMain`, because a live terminal reads its input box as keys, measured on Claude Code 2.1.319 and Codex 0.166 through `herdr agent prompt`: a leading `!` ran `echo` in bash mode with no approval, a leading `/clear` wiped the session, `ESC d` inside the text was taken for Alt+D and ate a character. So the text gets `CHAT_PREFIX` (`[飞书] ` / `[Telegram] `), loses its control characters (`sanitizeForAgent`; newlines stay, both agents took a multi-line paste as one submission), and is cut at 2000 characters.
- **When it goes in** (`mainState`, looked up by name every time with `lookupAgentByName`): `blocked` (Herdr says so, or `screenHasOpenMenu`) waits; `draft` waits, because `agent prompt` types after whatever is in the box and submits both (`草稿半句[飞书] …`), and `inputDraft` can only tell a draft from the box's placeholder by its styling (`readPaneScreenAnsi`: placeholders are dim, SGR 2; Codex's braille dots are coloured but are not text); `codex-busy` waits, because a Codex mid-turn takes the message into the current turn and drops what it had written so far; Claude Code mid-turn queues it itself (and Herdr then reports one done for both turns), so it is sent; idle / done / unknown is sent. A message that cannot go in is kept in `main-inbox.json`, in order, and `drainInbox` (every 5 s, behind `serial()`) sends the first one as soon as it can, one per pass. A main session with no name (drover re-registers it after `/clear` or a restart, and a Codex one only after its first message) gets `ABSENT_GRACE_MS` before the message is turned away; one still waiting after `LATE_NOTICE_MS` is mentioned once. `/send` clears the draft with `ctrl+u backspace` rounds (one line each; never `ctrl+c`, which interrupts or quits, nor `esc esc`, which opens rewind) and quotes what it cleared. Each delivery logs `main inbox · delivered|stashed|refused · <n> chars · …` to `poller.log`, never the text.
- **The answer to a chat message.** Each delivery adds `{ id, paneId, channel, messageId, text, deliveredAt }` to `main-pending.json` (6 h TTL). Every main done looks each one up in the session record (`sessionChatAnswers` → `claudeChatAnswer` / `codexChatAnswer` in `transcript.mjs`), never "the answer at the next done": live, a chat message was answered and a Monitor event started the next turn at once, Herdr saw no done between them, and the ping carried the Monitor turn's one-liner instead of the progress summary. Claude Code: the first user record after `deliveredAt` (2 s slack) whose text carries the sent text (queued messages are their own user records, sometimes in the middle of a turn), then the conversation up to the next input that starts a turn (a user record with text that is not a tool result or a `<system-reminder>`: the terminal, a queued message, a `<task-notification>`). With that boundary there, the answer is the end_turn text before it, else the last text before it; without it, the turn is answered only once it ends on end_turn text, otherwise it is open and waits for a later done (re-read 6 × 500 ms first, since the done can land before the record is written). Codex: the user `response_item` (or `user_message` event) carrying the text, then the next `task_complete`'s `last_agent_message`; a message that came in mid-task belongs to that task. No session record at all: the oldest waiting message gets this turn's answer. An answer goes back on the chat it came from, as a reply (`replyFeishu`, `im/v1/messages/{id}/reply`, falling back to an ordinary message if Feishu refuses; Telegram `reply_parameters`), and the record is removed once it went out. A blocked while a chat message waits is pinged at once, as a reply to it, instead of after the panel's wait.
- **Feishu is the only channel drover's users are shown.** drover's install guides the user to pair Feishu and never mentions Telegram, and Oncall's side of that is the setup hints and the README's "With drover" section. `setupHints({ drover })` gets `rolesActive()` from seed, install and `test`'s no-channel path: with nothing paired it offers Feishu alone, as `~/.drover/bin/drover oncall pair` (drover maps it to `pair-feishu`, which the next line names in case drover's command is not there), and no Telegram line at all, not even for a token already in `.env`. A Telegram the user paired themselves is still reported as `telegram: paired`. Without drover the output is the old one, line for line, and a test pins it. Telegram itself works with drover exactly as before (its own `[Telegram] ` prefix, its own sender check); the README says so once, in its Telegram section, and the "With drover" section mentions only Feishu. Keep it that way when touching either.

### Releases and updates (`.github/workflows/test.yml`, `src/lib/update.mjs`)

Herdr has no automatic plugin updates, but `herdr plugin update <id> --yes` does the hard part (src/cli/plugin.rs, 0.9.5): it refetches the ref recorded at install (`git fetch --depth 1 origin <ref>`), stops at "already up to date" when the commit has not moved, and otherwise checks out into a new installation directory and **runs the build steps there** (the panel is recompiled) before switching new invocations over, while running processes keep the old files. Reinstalling over an existing GitHub install is allowed; over a linked checkout it is refused. The `.env` lives in the config dir and the state in the state dir, both keyed by plugin id, so neither moves.

So releases are a branch. The `release` job in `test.yml`, on a push to `main` once the `node` and `macos` jobs pass, reads `version` from the manifest and, if `v<version>` is not released yet, creates the GitHub release from that commit (subject as title, the rest as notes) and force-moves the `stable` branch to it. A push that keeps the version releases nothing, so commits between releases never reach installs. The README installs with `--ref stable`, which records that ref.

`updateLoop` in the poller runs `checkForUpdate` at start and every 6 h (with a 30 min floor between checks, in `<state>/update-check.json`, since the poller restarts on every Herdr start and config action). It reads this plugin's `source` from `herdr plugin list --json --plugin <id>`: `kind: "local"` (a checkout linked by `install.sh`) is never touched, and `AUTO_UPDATE=0` stops it before any call. A GitHub install whose `requested_ref` is not `stable` (installed before releases existed, following the default branch) is reinstalled once with `--ref stable`, when that branch exists; otherwise it is `plugin update`. A changed `resolved_commit` afterwards is an update: the paired chats get `oncall updated · v<from> → v<to>` with the release URL, then the new installation's `poll` action is invoked, which restarts the poller from the new code and stops the old one. The herdr calls go through `runHerdrAsync`, since an update builds for a minute and the poller must keep answering meanwhile.

### Talking to Herdr

All Herdr calls go through `runHerdr()` (`spawnSync` of `HERDR_BIN_PATH` or `herdr`). Herdr's JSON shapes are not stable, so `extractAgentStatus` and `extractReadText` in `src/lib/herdr.mjs` probe several nestings, and `readPaneScreen` tries a list of command variants in order. When adding a new Herdr call, follow the same defensive pattern rather than assuming one shape.

`src/lib/index.mjs` re-exports every lib module; import from it (`../lib/index.mjs`) rather than from individual files.

## Conventions and non-goals

- The plugin id is fixed at `com.codreamer.herdr.oncall`. Do not create `oncall.telegram` / `oncall.app` variants; new channels are a `CHANNEL` value, not a new plugin. `OLD_PLUGIN_IDS` in `paths.mjs` exists only so install can unlink legacy ids.
- Telegram and Feishu messages are plain text, no emoji (tests assert this for both), no Markdown parse mode, no rich-text card elements.
- The location line (`formatWhere`) is `repo · task · space · tab · pane N`, and the desktop panel shows it as its heading with `status · Agent` underneath in small grey — which task it is matters more than what state it is in. The *task* segment is a linked worktree's own directory name (branch appended in parens only when it is not the same slug — `build_deploy_plan` vs `build-deploy-plan` counts as the same), or, for an ordinary checkout, the branch — including `main`, which is as much a fact as any other branch. `resolveWorktree` gets all of it from one `herdr worktree list --workspace <id>` call: `workspace get` only carries a `worktree` block for worktree-backed workspaces, so an ordinary repo used to show nothing but its workspace label. The space segment is dropped when it just repeats the repo or the task.
- Never send the full pane transcript: blocked → dialog tail, done → the last answer only (from the agent's session record, else the screen). On the screen path, `doneSnippet` finds that turn by slicing below the last user marker, and `isUserMarker` cannot tell a sent turn from a prompt box, which is drawn the same way (Claude Code `❯ <whatever is typed>`, Codex `› Ask Codex to do anything`); the structural check above handles a screen with turn markers, and otherwise an empty slice falls back to the tail, because below the box there is only chrome. That mattered once the mode footer stopped being recognised: `⏵⏵ accept edits on (shift+tab to cycle)` was chrome by its key hint, but with monitors or agents attached Claude Code drops the hint (`⏵⏵ accept edits on · 1 monitor · ← 1 agent`) and nothing else matched — a done panel opened with that one footer line as its entire body. The `⏵⏵` marker is what makes it a footer, not what it goes on to say. Codex's footer (`GPT-6-Astra high · ~/repo · branch`, `← for agents · ? for shortcuts …`) is chrome by its shape — a model name, one word, a dot, then a path — and the `? for shortcuts` hint; the effort word is deliberately not listed (one machine said `high`, the next `ultra`). A repainting Codex pane needs this so its box-and-footer read does not settle as an answer.
- Only `TELEGRAM_CHAT_ID` and `FEISHU_OPEN_ID` may drive panes; keep the sender check in both the message and the button path of each channel.
- `CHANNEL` picks where pings go among the *paired* channels (default `telegram`); replies are accepted from every paired channel regardless.
- Scripts that fail exit `0` when the plugin is simply unconfigured or disabled (so Herdr doesn't log noise) and non-zero only for real errors.
